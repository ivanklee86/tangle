# Screenshot tests and generated documentation screenshots

Status: in progress · 2026-11-26 · [#294](https://github.com/ivanklee86/tangle/issues/294)

Exploratory testing of the multi-source UI found visual regressions that every functional test passed: a dark-mode row background that didn't exist in the palette, a table overflowing its container, alerts unreadable in dark mode, an invisible checked checkbox. Functional tests assert text and roles, so they can't see any of these. This adds Playwright screenshot comparisons, and uses the same machinery to regenerate the README's screenshots.

## Approach

- **One realistic fixture fleet** (`web/e2e/fixtures/fleet.ts`): two ArgoCDs (`prod`, `staging`), applications named like a real fleet, every health and sync state, single- and multi-source applications, and a diff responder that answers each application the way the server would for the query's target ref, target repos and inference. It's served with Playwright's request routing, like the mocked suite, so no backend is needed and nothing on screen varies between runs.
- **Screenshot tests** (`web/e2e/visual/`): `expect(page).toHaveScreenshot()` for the states that regressed, in light and dark. Baselines are committed next to the specs.
- **Documentation screenshots** (`web/e2e/docs/`): the same fixtures, written to `docs/images/Tangle{Home,Applications,Diffs}.png` instead of compared. This replaces `web/scripts/capture-readme-screenshots.mjs`, which needed the live stack and showed the integration fixtures (`test-1`, `env:test`). `TangleCLI.png` is a terminal screenshot and stays manual.
- **One rendering environment**: both run inside `mcr.microsoft.com/playwright:v1.65.1-noble`, the image for our pinned Playwright, through `web/scripts/playwright-docker.sh`. Locally that's a `task` command, and CI runs the same script on the amd64 runner. Fonts and anti-aliasing differ between machines and architectures, so a baseline is only valid in the environment that made it.
- **Separate config** (`web/playwright.visual.config.ts`), so `playwright test` with the default config still runs only the mocked suite on the host, as CI's `ts` job does.

## Inside the container

The repo is bind-mounted, and the script runs as the host user, so written files (baselines, docs images, test results) are owned by you. `node_modules`, `.svelte-kit` and `build` are container-only `tmpfs` mounts. That keeps a container `npm ci` from replacing the host's `node_modules`, and keeps `svelte-kit sync` from rewriting the `.svelte-kit/generated` files a running `vite dev` reads (it writes an empty `PUBLIC_BASE_URL`, which breaks the dev server).

## Tasks

- `task ts:test:visual`: compare against the baselines.
- `task ts:test:visual:update`: regenerate the baselines, after an intended UI change or a dependency update that moves pixels.
- `task ts:screenshots`: regenerate the documentation screenshots.

## CI

A `visual` job on the amd64 runner runs `web/scripts/playwright-docker.sh --project=visual`. On failure it uploads `test-results/`, which holds the expected, actual and diff images for each failed screenshot.

## Not in this change

- Component-level screenshots with Vitest browser mode.
- A hosted review service (Argos, Lost Pixel).
- Checking in CI that the documentation screenshots are current. They're regenerated by hand, and the screenshot tests cover the same screens.
